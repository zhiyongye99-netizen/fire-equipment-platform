下面分两部分讲：**一是微信小程序上线需要哪些线上服务，二是 Git 到底怎么用、在你这个项目里怎么用。**

# 一、微信小程序架构到微信上，还需要哪些线上服务？

先把概念说清楚：微信小程序本身只是在微信里运行的“前端界面”。  
它不能单独完成全部业务。你的项目还需要一整套线上服务支撑：

```txt id="3w0ndq"
微信小程序前端
↓
后端 API 服务
↓
数据库
↓
文件存储
↓
管理后台
↓
微信开放能力
↓
运维监控和安全体系
```

微信小程序可以由企业、政府、媒体、其他组织或个人等主体注册；企业、政府、媒体、其他组织类型的小程序通常需要微信认证，微信认证在公开资料中通常为 300 元/次。小程序运行在微信生态内，用户可以通过扫码、搜索、微信内入口访问。([zh.wikipedia.org](https://zh.wikipedia.org/wiki/%E5%BE%AE%E4%BF%A1%E5%B0%8F%E7%A8%8B%E5%BA%8F?utm_source=chatgpt.com))

---

## 1. 微信小程序账号

你首先需要一个小程序账号。

建议主体用：

> **企业主体，不建议个人主体。**

因为你的项目涉及：

- 供应商入驻；
- 消防装备信息；
- 企业服务；
- 线索撮合；
- 资料下载；
- 后期可能接微信支付；
- 后台管理；
- 商业服务。

个人主体在能力、类目、认证和商业化方面会受限制。

你需要准备：

| 项目 | 说明 |
|---|---|
| 小程序账号 | 在微信公众平台注册 |
| 企业主体 | 营业执照、法人/管理员信息 |
| 微信认证 | 用于开放更多能力 |
| 小程序名称 | 建议先不要用太官方、太像政府机构的名称 |
| 服务类目 | 要根据实际功能选择 |
| 小程序头像 / 简介 | 需要合规、准确 |
| 隐私政策 | 必须准备 |
| 用户协议 | 建议准备 |
| 内容审核机制说明 | 社区、资讯、供应商发布都需要 |

名称上建议慎重，不要使用容易让人误解为官方机构的小程序名，例如“国家消防装备采购平台”这类名称不建议使用。可以考虑：

- 消防装备智选
- 消防装备通
- 消防装备参考
- 应急装备智选
- 消防车辆装备库

---

## 2. 后端 API 服务

小程序前端不能直接访问数据库。  
它需要访问后端接口。

比如：

```txt id="ceul7s"
小程序点击“产品详情”
↓
请求后端 API
↓
后端查询数据库
↓
返回产品参数、图片、供应商、资料状态
```

你的项目需要的后端 API 包括：

| 模块 | 后端 API 要做什么 |
|---|---|
| 用户登录 | 微信登录、手机号绑定、身份认证 |
| 首页资讯 | 获取文章、专题、推荐位 |
| 装备库 | 获取分类、产品列表、产品详情 |
| 参数对比 | 获取多个产品参数并比较 |
| 收藏 | 添加收藏、取消收藏、查看收藏 |
| 询价线索 | 发起询价、供应商查看、跟进 |
| 消防圈 | 发帖、评论、点赞、审核 |
| 供应商后台 | 产品录入、资料上传、线索管理 |
| 平台后台 | 审核、权限、内容管理 |
| 文件资料 | 彩页、证书、报告的上传和下载 |
| 消息通知 | 站内通知、审核通知、线索提醒 |

建议你使用：

> **NestJS + PostgreSQL + Prisma**

这和我们前面准备给 Codex 的文档是一致的。

---

## 3. 数据库服务

数据库是存业务数据的地方。

你这个项目至少要存：

- 用户信息；
- 消防单位信息；
- 供应商信息；
- 产品信息；
- 装备分类；
- 参数模板；
- 产品参数；
- 检测报告、认证证书索引；
- 询价线索；
- 消防圈帖子；
- 评论；
- 收藏；
- 对比记录；
- 审核记录；
- 操作日志。

建议数据库：

| 方案 | 是否推荐 | 说明 |
|---|---|---|
| PostgreSQL | 推荐 | 适合复杂结构、后期支持全文检索和向量检索 |
| MySQL | 也可以 | 国内团队熟悉度高 |
| MongoDB | 暂不优先 | 参数结构灵活，但权限、事务、统计会复杂 |
| 微信云开发数据库 | 适合 MVP，但后期扩展可能受限 | 简单快速，但复杂后台和数据分析能力有限 |

我的建议是：

> 如果目标是认真做成平台，优先 PostgreSQL。  
> 如果只是快速验证小程序 MVP，可以考虑微信云开发。

## 4. 文件存储服务

你的项目会有大量文件：

- 产品图片；
- 产品彩页 PDF；
- 检测报告；
- 认证证书；
- 说明书；
- 视频；
- 供应商资质；
- 招标文件样例；
- 图片素材。

这些文件**不要直接存在数据库里**，也不要直接放代码仓库里。

应该放对象存储：

| 服务 | 说明 |
|---|---|
| 腾讯云 COS | 和微信生态、腾讯云结合较方便 |
| 阿里云 OSS | 国内常用 |
| 七牛云 | 图片处理方便 |
| 微信云开发存储 | 适合小规模 MVP |

数据库里只保存：

- 文件名称；
- 文件类型；
- 文件地址；
- 所属产品；
- 所属供应商；
- 是否公开；
- 审核状态；
- 上传时间；
- 下载权限。

## 5. 域名和 HTTPS

如果你不用微信云开发，而是自建后端服务器，就需要：

| 项目 | 说明 |
|---|---|
| 域名 | 例如 `api.xxx.com` |
| HTTPS 证书 | 小程序正式环境必须使用 HTTPS |
| 服务器域名配置 | 在微信小程序后台配置 request 合法域名 |
| 备案 | 中国大陆服务器通常需要 ICP 备案 |
| CDN | 图片、PDF、视频下载建议走 CDN |
| 防盗链 | 防止资料被外部滥用 |

你作为初学者，记住一句话：

> 小程序正式上线，不能随便请求一个临时 IP 地址或本地地址，必须配置合法 HTTPS 域名。

## 6. 服务器 / 云服务

你需要一个地方运行后端服务和后台系统。

常见选择：

| 方案 | 适合情况 |
|---|---|
| 腾讯云轻量应用服务器 | 入门成本低 |
| 腾讯云 CloudBase / 云开发 | 小程序快速上线 |
| 阿里云 ECS | 通用可靠 |
| Vercel / Render 等海外服务 | 国内访问和备案可能有问题，不建议作为中国用户主服务 |
| Docker + 云服务器 | 后期更规范 |
| Kubernetes | 第一阶段没必要 |

你的项目第一版可以这样选：

### 稳妥方案

```txt id="l6jfj5"
腾讯云服务器
+ PostgreSQL
+ 腾讯云 COS
+ HTTPS 域名
+ 微信小程序
+ Next.js 后台
+ NestJS API
```

### 快速 MVP 方案

```txt id="72k6k3"
微信云开发
+ 云数据库
+ 云存储
+ 云函数 / 云托管
+ 小程序前端
```

如果你后期要做复杂供应商后台、平台后台、数据分析、AI 知识库，我更倾向于前一种。

## 7. 管理后台线上部署

你不只有小程序，还需要两个后台：

```txt id="42lshi"
供应商 PC 后台
平台运营后台
```

它们不能只在本地电脑运行，后期要部署到线上。

需要：

- 后台域名，例如 `admin.xxx.com`；
- 供应商后台域名，例如 `supplier.xxx.com`；
- 管理员登录；
- 权限控制；
- HTTPS；
- 操作日志；
- 文件上传；
- 数据备份。

↓

↓

↓

可以考虑：

| 类型 | 用途 |
|---|---|

## 10. 内容审核与安全服务

你的项目有首页资讯、消防圈、供应商发布、评论、图片上传，这都需要审核。

至少要做：

- 敏感词过滤；
- 图片审核；
- 帖子审核；
- 评论举报；
- 供应商发布标识；
- 用户评价审核；
- 操作日志；
- 黑名单；
- 管理员审核后台。

移动超级 App 和小程序生态存在复杂 API 与安全边界问题，研究也指出小程序/超级 App 环境中的隐藏 API 和权限问题可能带来安全风险，所以敏感数据、权限判断和核心业务逻辑不能只放在前端，必须放在后端。([arxiv.org](https://arxiv.org/abs/2306.08134?utm_source=chatgpt.com))

# 三、Git 是什么？用最通俗的话讲

Git 可以理解为：

> **程序开发里的“时间机器 + 版本保险箱 + 协作记录本”。**

它解决三个问题：

## 1. 改错了可以回退

你让 Codex 改代码，万一它改坏了，Git 可以回到上一个正常版本。

## 2. 每次修改都有记录

你可以知道：

- 谁改了什么；
- 什么时候改的；
- 为什么改；
- 哪些文件被改。

## 3. 可以开分支做实验

比如：

- 主线保持稳定；
- 单独开一条分支做供应商后台；
- 做坏了不影响主线；
- 做好了再合并。

---

# 四、Git 里的几个核心概念

## 1. 仓库 Repository

就是一个被 Git 管理的项目文件夹。

例如：

```txt id="rcwh1x"
fire-equipment-platform/
```

里面有代码、文档、图片、配置文件。

---

## 2. 提交 Commit

提交就是保存一个版本快照。

你可以理解为：

> “我现在把这个阶段的成果存档。”

例子：

```bash id="pbh71o"
git commit -m "docs: add product requirements"
```

意思是：

> 保存一次，说明是“增加产品需求文档”。

---

## 3. 分支 Branch

分支就是一条独立开发路线。

例如：

```txt id="8fcvx2"
main                      稳定版本
develop                   开发版本
feature/equipment-page    正在做选装页
feature/supplier-admin    正在做供应商后台
```

你可以把它理解为：

> 主路旁边开一条临时施工便道。

施工完成、检查合格，再并回主路。

---

## 4. 合并 Merge

把一个分支的成果合并到另一个分支。

比如：

```txt id="kwn7zu"
feature/equipment-page → develop
```

意思是：

> 选装页开发完成，合并到开发主线。

---

## 5. 远程仓库 Remote

远程仓库就是云端备份，比如 GitHub、GitLab、Gitee。

本地电脑坏了，远程仓库还能保存代码。

对你来说建议：

- 如果项目不涉密，可以用 GitHub 私有仓库；
- 如果希望国内访问方便，可以用 Gitee 私有仓库；
- 如果资料较敏感，注意不要上传内部原始资料。

---

## 6. 工作区 Working Directory

就是你电脑上正在编辑的项目文件夹。

---

## 7. 暂存区 Stage

Git 提交前有一个“待提交区”。

你先把要提交的文件放进去：

```bash id="9nicy9"
git add .
```

再提交：

```bash id="stnttr"
git commit -m "message"
```

可以理解为：

> 先把要归档的文件放进文件篮，再正式存档。

---

# 五、你每天实际怎么用 Git？

你只要先掌握 8 个命令。

## 1. 查看当前状态

```bash id="37cfef"
git status
```

作用：看看哪些文件被改了。

---

## 2. 把所有改动加入暂存区

```bash id="bp16nl"
git add .
```

作用：准备提交所有修改。

---

## 3. 提交一次版本

```bash id="0gbh2z"
git commit -m "docs: update PRD"
```

作用：保存一个版本。

---

## 4. 查看提交记录

```bash id="jr53f6"
git log --oneline
```

作用：看历史版本。

---

## 5. 创建新分支

```bash id="0lejkr"
git checkout -b feature/equipment-page
```

作用：创建并切换到一个新分支。

---

## 6. 切换分支

```bash id="kb1n0s"

```

作用：切换回开发主线。

---

## 7. 合并分支

```bash id="03z2ol"
git merge feature/equipment-page
```

作用：把功能分支合并到当前分支。

---

## 8. 推送到远程仓库

```bash id="vzn82q"

```

作用：上传到 GitHub / Gitee。

# 六、你的项目推荐 Git 分支架构

对初学者，别搞太复杂。建议三层：

```txt id="ry3hli"
main        稳定版本
develop     开发集成版本
feature/*   具体功能分支
```

## main

只放稳定、可运行版本。

不要直接在 main 上开发。

---

## develop

所有开发完成的功能先合并到 develop。

---

## feature 分支

每个功能一个分支。

例如：

```txt id="75d8yr"
feature/project-scaffold
feature/database-schema
feature/supplier-admin
feature/platform-admin
feature/miniapp-equipment
feature/miniapp-community
feature/miniapp-mine
feature/supplier-mobile
```

# 七、你的项目实际开发流程

## 第一步：初始化 Git

在项目根目录：

```bash id="52yk8y"
git init
git add .
git commit -m "init: add project docs and rules"
```

---

## 第二步：创建 develop 分支

```bash id="33nz4b"
git checkout -b develop
git push -u origin develop
```

如果还没有远程仓库，可以先不 push。

---

## 第三步：每个功能开一个分支

例如做项目骨架：

```bash id="kruop1"
git checkout -b feature/project-scaffold
```

让 Codex 在这个分支工作。

完成后：

```bash id="2rk4th"
git status
git add .
git commit -m "chore: create project scaffold"
git checkout develop
git merge feature/project-scaffold
```

---

## 第四步：开发数据库

```bash id="otu7mu"
git checkout -b feature/database-schema
```

让 Codex 做数据库。

完成后：

```bash id="yscv83"
git add .
git commit -m "feat: add database schema"
git checkout develop
git merge feature/database-schema
```

---

## 第五步：逐步做功能

按顺序：

```txt id="x1dstk"
feature/supplier-admin
feature/platform-admin
feature/miniapp-equipment
feature/miniapp-community
feature/miniapp-mine
feature/supplier-mobile
```

# 八、你使用 Codex 时，Git 怎么配合？

每次让 Codex 做事前，先确认：

```bash id="j2qjz7"
git status
```

如果有未提交文件，先提交。

然后告诉 Codex：

```txt id="ia6lae"
当前分支是 feature/miniapp-equipment。
请只实现选装首页，不要修改数据库模型和后台代码。
完成后运行 pnpm lint、pnpm typecheck、pnpm test。
```

Codex 完成后，你检查：

```bash id="5brvxz"
git status
```

如果满意：

```bash id="ogsimr"
git add .
git commit -m "feat: implement miniapp equipment home"
```

如果不满意，可以回退。

# 九、Git 回退怎么做？

## 1. 只想放弃当前未提交修改

```bash id="41b1p5"
git restore .
```

意思是：把工作区恢复到上一次提交。

注意：会丢掉当前没提交的修改。

---

## 2. 想回到上一个提交

```bash id="s33v9n"
git reset --hard HEAD~1
```

意思是：退回到上一个版本。

初学者慎用。

---

## 3. 查看历史版本

```bash id="2nlwrn"
git log --oneline
```

看到类似：

```txt id="8probu"
a1b2c3d feat: add equipment page
d4e5f6g chore: create scaffold
```

可以回到某个版本：

```bash id="aacqf0"
git checkout a1b2c3d
```

# 十、GitHub / Gitee 要不要用？

建议用，但要注意资料安全。

## 适合上传

- 代码；
- PRD；
- AGENTS.md；
- 配置模板；
- 样例数据；
- UI 参考图；
- 脱敏文档。

## 不适合上传

- 供应商未授权彩页全集；
- 内部招标资料；
- 联系人手机号；
- `.env`；
- 密钥；
- 证书；
- 数据库备份；
- 商业报价底线。

`.gitignore` 文件里要明确排除：

```txt id="mox8tw"
.env
.env.local
*.pem
*.key
node_modules/
dist/
.next/
database_backup/
private-materials/
```

# 十一、初学者最容易犯的 Git 错误

## 1. 不提交就让 AI 大改

风险：改坏了无法回退。

正确做法：每次让 Codex 修改前，先 commit。

---

## 2. 在 main 上直接开发

风险：稳定版本被破坏。

正确做法：main 只放稳定版本，开发在 feature 分支。

---

## 3. 提交 `.env` 和密钥

风险：密钥泄露。

正确做法：只提交 `.env.example`，不提交 `.env`。

---

## 4. 一次提交太多内容

风险：以后排查困难。

正确做法：一个功能一次提交。

---

## 5. 提交信息乱写

不要写：

```bash id="t9kdt2"
git commit -m "改了一下"
```

建议写：

```bash id="ql042g"
git commit -m "feat: add supplier lead detail page"
git commit -m "docs: update UI reference rules"
git commit -m "fix: prevent supplier viewing other leads"
```

---

# 十二、推荐提交信息格式

你可以采用简单规则：

| 前缀 | 含义 |
|---|---|
| `docs:` | 文档 |
| `feat:` | 新功能 |
| `fix:` | 修复 |
| `chore:` | 配置、脚手架 |
| `refactor:` | 重构 |
| `style:` | 样式 |
| `test:` | 测试 |

例子：

```bash id="atnfpa"
git commit -m "docs: add product requirement documents"
git commit -m "chore: setup monorepo scaffold"
git commit -m "feat: add equipment comparison page"
git commit -m "fix: hide user phone from supplier"
```

# 十三、给你的 Git 最小操作手册

你先记住这个日常流程就够了：

```bash id="ss4rcb"
# 1. 查看状态
git status

# 2. 创建功能分支
git checkout -b feature/xxx

# 3. 让 Codex 修改代码

# 4. 查看改了什么
git status

# 5. 提交
git add .
git commit -m "feat: xxx"

# 6. 回到开发主线
git checkout develop

# 7. 合并
git merge feature/xxx
```

如果你不会命令，也可以让 Codex 帮你执行，但你要先让它说明每一步在做什么。

# 十四、你现在接下来应该做什么

建议你按这个顺序：

1. 下载并解压 V4 迁移包。
2. 建一个新项目文件夹。
3. 初始化 Git。
4. 提交第一版文档。
5. 创建 `develop` 分支。
6. 打开 Codex。
7. 先让 Codex 只阅读文档，不写代码。
8. 确认理解正确后，再创建 `feature/project-scaffold` 分支。
9. 让 Codex 搭项目骨架。
10. 每完成一个阶段就 commit。

第一条给 Codex 的任务仍然是：

```txt id="bt3qpf"
请先阅读 AGENTS.md 和 docs/ 下所有文档，不要写代码。
请复述你对项目目标、产品边界、技术栈、页面范围、用户角色、数据模型、UI 参考图使用规则、第一阶段开发顺序的理解。
```

这样最稳。
